### 2. Gerbang Moderasi Laporan Publik
Kolom `moderation_status` (`PENDING`/`APPROVED`/`REJECTED`) yang sebelumnya ada di skema DB tapi tidak dipakai sama sekali — sekarang aktif. Laporan publik (`isPublic=1`) baru tayang di Umpan Publik setelah disetujui Moderator/Super Admin lewat section "Moderasi Publikasi" di panel admin.

**Migrasi aman untuk data lama**: `server/db/connection.ts` menambah kolom `moderation_status` secara defensif kalau production DB belum punya (`ALTER TABLE`), lalu sekali jalan (guarded lewat tabel `settings`) meng-`APPROVED`-kan semua laporan publik yang sudah ada sebelum fitur ini — supaya tidak tiba-tiba hilang dari feed publik.

**File kunci**: `server/routes/reports.ts` (`PATCH /:id/moderation`), `src/components/AdminPanel.tsx` (section Moderasi Publikasi + filter chip "Moderasi"), `src/components/PublicFeed.tsx` (filter tambahan `moderationStatus === "APPROVED"`).

### 3. Ekspor Laporan ke Excel
Tombol "Unduh Excel" di Admin Panel, endpoint `GET /api/reports/export` (pakai `exceljs`) yang otomatis discope sesuai role login (Moderator → divisinya saja, Staff → tiket miliknya, Super Admin/Pimpinan → semua). Kolom: Kode Tiket, Judul, Kategori, Urgensi, Status, Status Publikasi, Status Moderasi, data pelapor, tanggal.

### 4. Kompresi Otomatis Lampiran Bukti
Lampiran gambar (opsional saat submit laporan) sekarang otomatis dikompres di browser (canvas API, tanpa library tambahan) sampai di bawah 2MB kalau ukurannya lebih besar — supaya user tidak gagal submit gara-gara foto HP terlalu besar. PDF di atas 2MB ditolak dengan pesan jelas (tidak bisa dikompres otomatis di browser). Limit server (`multer`) diturunkan dari 10MB ke 2MB sebagai jaring pengaman, konsisten dengan batas frontend.

**File kunci**: `src/utils/imageCompression.ts` (baru), `src/components/ReportForm.tsx`, `server/routes/uploads.ts`.

### 5. Ubah Kategori Laporan (Fix Wrong-Division Routing)
Sebelumnya, laporan yang salah kategori saat disubmit (mis. isinya akademik tapi kepilih kategori "Layanan Administrasi & Staf") **permanen terkunci ke divisi yang salah** — tidak ada cara mengubahnya, bahkan Super Admin tidak bisa mendisposisikan ke staf divisi yang benar. Sekarang ada endpoint `PATCH /api/reports/:id/category` (Super Admin & Moderator, sama seperti wewenang disposisi) di section baru "Ubah Kategori" pada panel detail laporan, ditempatkan sebelum "Disposisi Tugas".

Kalau kategori baru membuat laporan pindah divisi, disposisi lama **otomatis direset** (supaya staf divisi lama tidak lagi kebagian tugas yang bukan urusannya) dan tercatat di linimasa laporan sebagai jejak audit. Kalau kategori baru masih di divisi yang sama, disposisi lama tidak ikut terhapus. Sudah diuji end-to-end: laporan berpindah scope Moderator dengan benar setelah kategori diubah.

### 🔴 Insiden yang Ditemukan & Ditutup: Tombol Dev-Login Bocor ke Production
Setelah deploy pertama, tombol dev-login sempat **muncul di production** (https://tbe-fit.uii.ac.id/lapor/) — root cause: `vite build` polos cuma default ke mode production **kalau** `NODE_ENV` belum ter-set; shell VPS ternyata punya `NODE_ENV` ambient yang bikin build jatuh ke mode development meski perintahnya "build". **Sudah diperbaiki**: `package.json` build script dipaksa `vite build --mode production` (tidak bisa dibajak env ambient) + guard hostname di `LoginGate.tsx` sebagai defense-in-depth. Diverifikasi lokal: build ulang dengan `NODE_ENV=development` dipaksa, tombol tetap tidak muncul. **Tidak ada eksposur berbahaya** — backend tetap menolak endpoint-nya di production terlepas dari tombolnya muncul atau tidak.

## ⚠️ Pelajaran Penting: Local Uncommitted Changes di VPS
Sempat terjadi deploy yang "sukses" (`npm run build` jalan tanpa error, `pm2 restart` sukses) tapi **kode baru sama sekali tidak masuk** — penyebabnya `git pull` gagal diam-diam karena ada perubahan file yang di-edit langsung di VPS tanpa commit (`src/components/LoginGate.tsx`, typo fix "civitas"→"sivitas" yang ditambal manual via SSH). Git pull menampilkan error "local changes would be overwritten", tapi karena command berikutnya (`npm install`, `npm run build`, `pm2 restart`) tetap dijalankan berurutan, terlihat seperti sukses padahal build ulang cuma pakai kode lama.

**Selalu verifikasi setelah deploy**: cek `git log --oneline -1` menunjukkan commit hash yang benar SETELAH `git pull`, sebelum lanjut ke `npm run build`. Kalau pull gagal karena local changes, cek dulu `git diff <file>` — kalau isinya sudah termasuk di commit yang masuk (biasanya karena pernah ditambal manual di VPS), aman pakai `git checkout -- <file>` lalu pull ulang.
